# ADR 0008: Developer Onboarding

**Status:** Accepted — implemented
**Date:** 2026-09-09

## What was built

- `app/onboarding/` — deterministic repository-understanding and the
  narrow AI-generation surface:
  - `manifest.py` — best-effort dependency-manifest parsing for the four
    ecosystems the indexer already supports (`package.json`,
    `pyproject.toml` — PEP 621 and Poetry — `requirements.txt`, `go.mod`).
  - `setup.py` — presence-based development-setup step detection
    (`find_shallowest` handles monorepo-nested manifests, e.g. this
    project's own `backend/pyproject.toml`).
  - `heuristics.py` — entry-point/README/auth-file detection and the
    fixed-category learning-path builder.
  - `context.py` — aggregates all of the above plus
    `app/architecture/graph_builder.py`'s package graph and a new
    `rank_files_by_dependents` (file-level fan-in ranking, added to that
    module rather than reimplemented) into one `OnboardingContext`.
  - `prompt.py` / `result_schema.py` — the single LLM call that produces
    the guide's narrative sections, with the same citation-validation
    pattern as ADR 0007.
- `OnboardingGuide` (new table) — one row per generation, keyed by the
  repository's latest **successfully indexed** commit_sha; `OnboardingProgress`
  (new table) — one row per (user, item) marked complete.
- `GET/POST /repositories/{id}/onboarding`, `GET/PUT
  .../onboarding/progress[/{item_key}]` — the trigger/poll pattern from
  ADR 0004/0007, plus per-user progress tracking.
- Frontend: `/onboarding` (repository picker) and
  `/repositories/{id}/onboarding` (the guide) — eight sections matching
  the brief's own list, a "Start Here" learning-path sidebar, and a
  completion progress bar. `Mark as complete` toggles persist per user.

## Decisions and why

### Most of the guide is not AI-generated at all

The brief's own instruction — "Use AI only where useful. Do not generate
meaningless AI text." — is the load-bearing design constraint here, not a
footnote. Of the seven "Generate" items in the brief, only four go
through the LLM at all:

| Section | Generated by |
|---|---|
| Repository overview | Live `Repository` row — no generation needed, it already exists |
| Architecture overview | **AI**, grounded in the package graph |
| Important modules | `graph_builder.build_package_graph`, ranked by file count |
| Recommended files | `graph_builder.rank_files_by_dependents` (fan-in) |
| Development setup | `onboarding/setup.py` — presence-based, deterministic |
| Common workflows | **AI**, grounded in route/service files |
| Key dependencies | `onboarding/manifest.py` — parsed, not summarized |
| Database structure | `heuristics.find_database_structure` — indexed model/repository classes |
| Authentication flow | **AI** — and explicitly **skipped** (left `null`) if no auth files exist |
| FAQ | **AI**, each answer required to cite real files |
| Learning path | `heuristics.build_learning_path` — fixed categories, real files |

A dependency list, a file listing, or an install command has exactly one
correct answer once the repository's actual manifests and file layout
are known — asking an LLM to reproduce that from scratch would be slower,
costlier, and strictly more likely to be wrong than just reading the
data. AI is reserved for the four things that genuinely require
synthesizing prose from structured facts: describing how modules relate,
describing a request flow, describing an auth flow, and writing FAQ
answers.

### Authentication flow is `null`, not invented, when there's no evidence

`heuristics.find_auth_files` matches on path and symbol-name conventions
(`auth`, `login`, `session`, `token`, `oauth`, `jwt`). When it finds
nothing, the prompt tells the model to set `authentication_flow` to
`null` rather than describe a generic auth flow that doesn't exist in
this repository — and the frontend renders that as an explicit "No
authentication-related files were detected" message, not a blank
section. This is the same principle as ADR 0007's citation validation
applied one level earlier: don't let the model fill a gap with plausible
-sounding text when there's no real data behind it.

### The learning path is fixed categories, not a free-form AI list

The brief's own "START HERE" example (`README → entry point → auth →
database → routing → payment service`) is a sequence of **roles**, not
arbitrary suggestions — every repository has (or doesn't have) a README,
an entry point, an auth layer, and so on. `heuristics.build_learning_path`
walks that fixed list of categories and, for each one, either finds the
real file that plays that role in *this* repository or skips the step
entirely (no README found -> no "1. README" step invented). The final
slot — matching the brief's own "Payment service" — is filled by
whichever real "service"-kind file has the most fan-in in this specific
repository, deduplicated against anything already used earlier in the
path. This produces a per-repository learning path without ever asking
the model to invent one.

### The guide is cached by the repository's last successful index, not the PR-style head_sha

There's no single "commit" a whole repository is "at" the way a pull
request has one head_sha — the closest equivalent is the commit the last
successful `IndexingJob` actually indexed (a new
`indexing_job_repository.get_latest_succeeded_for_repository`). Triggering
generation with no successful index yet raises `RepositoryNotIndexedError`
(409) rather than generating a guide from empty data. Re-indexing at a
new commit is what invalidates a cached guide — viewing the onboarding
page never triggers regeneration by itself, following the same
cache-is-the-table design as `PullRequestAnalysis` (ADR 0007).

### Generation runs on arq, mirroring PR analysis exactly

`generate_onboarding_guide` is a third arq task alongside indexing, sync,
and PR analysis — no new concurrency pattern. The one-completion-call
design (all four AI sections requested in a single JSON object) mirrors
PR analysis's single-call-per-analysis shape rather than four separate
LLM calls per guide.

### Progress tracking is a single generic table, not one column per section

`OnboardingProgress` has one `item_key` column rather than eight boolean
section columns plus a JSONB step-completion map. A completed item is a
row; an incomplete one doesn't exist — there's nothing else worth storing
once something is unmarked. `item_key` is either `section:<slug>` (one of
the eight fixed sections) or `step:<n>` (a learning-path step index),
which keeps the schema stable even though the guide's own section list
and learning-path length can both change across regenerations.

## What this phase does not do

- No cross-repository "your onboarding across all repos" dashboard — one
  repository's guide at a time, matching the brief.
- No per-organization customization of the fixed section list or the
  learning-path categories.
- The PR's/repository's free-text README is truncated
  (`_MAX_README_CHARS`, 6,000 chars) before being shown to the model —
  consistent with every other bounded-context decision in this codebase
  (ADR 0004/0005/0007), not a claim that longer READMEs are unsupported.
